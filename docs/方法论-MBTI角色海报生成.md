# 方法论：MBTI 角色海报生成

> 将已完成的 MBTI 角色分析报告、角色台词表、角色剧照三类材料，按照统一模板生成可直接发布的角色海报 PNG 图片。

---

## 一、任务定义

**输入**（三份材料 + 一份模板）：

| 材料 | 格式 | 说明 |
|------|------|------|
| MBTI 角色分析报告 | Markdown | 格式须符合 `方法论-图鉴类MBTI解读报告.md` 的产出规范 |
| 角色台词表 | Markdown | 按角色分组的编号台词列表 |
| 角色剧照 | jpg/png/webp | 每张图片文件名 = 角色名（如 `樊长玉.jpg`） |
| 海报 HTML 模板 | HTML | `templates/图鉴海报页模板.html` |

**输出**：
- 每个角色一张 PNG 海报图片（1080px 宽，2x 分辨率）
- 存放于指定输出目录

---

## 二、前置条件

### 2.1 环境依赖

```
Node.js >= 18
Python 3 + opencv-python-headless
npm 包：playwright
```

### 2.2 材料格式规范

以下格式规范是脚本解析的前提。材料若不符合这些格式，脚本将无法正确解析。

#### MBTI 角色分析报告（`.md`）

```markdown
# 作品名 · 人物 MBTI 深度解析

## 1）角色名 · XXXX（Xx-Xx-Xx-Xx）

**主导 Xx（功能全称）**：[论述正文]

**辅助 Xx（功能全称）**：[论述正文]

**第三 Xx（功能全称）**：[论述正文]

**劣势 Xx（功能全称）**：[论述正文]

**总结**：[总结正文]

---

## 2）角色名 · XXXX（Xx-Xx-Xx-Xx）
...
```

关键解析锚点：
- `## N）` 作为角色分隔符
- 首行 `角色名 · MBTI类型（功能栈）` 提取角色名、类型、功能栈
- `**主导/辅助/第三/劣势 XX（...）**：` 提取四个认知功能段
- `**总结**：` 提取总结段

#### 角色台词表（`.md`）

```markdown
## 1）角色名（MBTI类型）

1. "台词内容一"
2. "台词内容二"
3. "台词A"——"台词B"

---

## 2）角色名（MBTI类型）
...
```

关键解析锚点：
- `## N）` 作为角色分隔符
- 首行 `角色名（` 提取角色名
- `N. "..."` 或 `N. "..."——"..."` 提取台词，支持 `""`、`""`、`「」` 引号格式

#### 角色剧照

- 每个角色一张图片
- 文件名 = 角色名 + 扩展名（如 `谢征.jpg`），角色名必须与 MBTI 报告中完全一致
- 支持 `.jpg`、`.jpeg`、`.png`、`.webp`

## 三、执行步骤

### Step 1：准备配置文件

在 workspace 的对应项目目录下创建 `poster-config.json`：

```json
{
  "mbtiFile":   "workspace/XX图鉴/XX-MBTI角色分析.md",
  "quotesFile": "workspace/XX图鉴/XX-角色台词表.md",
  "photosDir":  "images/XX剧照",
  "outputDir":  "images/XX图文",
  "quotePicks": {
    "角色A": 3,
    "角色B": 1
  }
}
```

字段说明：
- 所有路径相对于项目根目录
- `quotePicks`：每个角色选用的台词编号（1-based），由人工指定。若未指定，默认使用该角色的第一条台词

### Step 2：执行生成脚本

```bash
node scripts/generate-posters.mjs workspace/XX图鉴/poster-config.json
```

脚本会自动完成以下流程：
1. 调用 `detect-faces.py` 对剧照目录做人脸检测，输出每张图的人脸中心坐标
2. 解析 MBTI 分析报告，提取角色数据（姓名、MBTI 类型、功能栈、四段功能解读、总结）
3. 解析台词表，按 `quotePicks` 配置选取指定台词
4. 为每个角色生成填充了内容的 HTML 文件
5. 用 Playwright 逐个截图为 PNG（2x 分辨率）

### Step 3：人工校验

**必须逐张检查以下项目**：

| 检查项 | 具体标准 | 常见问题 |
|--------|----------|----------|
| 人脸定位 | 角色正脸在 hero 区域内完整可见 | 侧脸/仰角照片检测偏移 |
| 台词完整 | 台词文字未被截断，引号配对正确 | 长台词溢出引用区 |
| 功能栈正确 | MBTI 类型、四个功能的缩写和位置与报告一致 | 解析错误导致功能缺失 |
| 正文分点 | 每个功能卡片内的正文被合理拆分为 2-3 个分点 + 1 条总结 | 短段落未拆分、拆分位置不自然 |
| 总结段 | 总结文字完整呈现在玻璃卡片内 | 文字溢出或截断 |
| 文字可读性 | 字号适中，行间距舒适，无文字重叠 | 超长段落导致卡片过高 |

### Step 4：问题修复

若校验发现问题：

- **人脸偏移**：检查 `detect-faces.py` 的检测结果，必要时在配置文件中新增 `faceOverrides` 字段手动覆盖
- **内容解析错误**：检查源 Markdown 文件的格式是否符合 Step 2.2 的锚点规范
- **台词调整**：修改 `poster-config.json` 中的 `quotePicks`，重新运行脚本

修复后重新执行 Step 2，脚本是幂等的，会覆盖已有输出。

## 四、产出要求

### 4.1 海报结构（从上到下）

每张海报包含以下模块，顺序固定：

```
┌──────────────────────────┐
│       角色剧照 hero       │  ← object-fit: cover, 人脸自动居中
│   （渐变融入背景底色）     │
├──────────────────────────┤
│  [MBTI 类型徽章]          │  ← 如 "INTJ"
│  角色名（大字）            │
│  功能栈（小字）            │  ← 如 "Ni - Te - Fi - Se"
├──────────────────────────┤
│  「角色台词」              │  ← 单条台词，带左侧金色竖线
├──────────────────────────┤
│  ┌─ 总结概述（玻璃卡片）─┐ │  ← 来自报告的 **总结** 段
│  │  完整总结文字          │ │
│  └────────────────────── ┘ │
├──────────────────────────┤
│  ○ 功能1（主导）          │  ← 圆形标签 + 功能卡片
│  │  ├─ 分点1             │     卡片内为树形思维导图结构
│  │  ├─ 分点2             │
│  │  └─ 总结线            │
│  ○ 功能2（辅助）          │
│  │  ...                   │
│  ○ 功能3（第三）          │
│  │  ...                   │
│  ○ 功能4（劣势）          │
│     ...                   │
└──────────────────────────┘
```

### 4.2 正文分点规则

功能解读的正文原本是一整段文字，在海报中需要拆成**树形分点结构**。拆分规则：

1. **拆分依据**：按中文句号 `。` 和分号 `；` 作为断句点
2. **合并短句**：连续的短句（合计 < 80 字符）合并为一个分点，避免碎片化
3. **目标数量**：每个功能卡片内 2-3 个分点为宜
4. **最后一句作为总结线**：原文的最后一句独立为带虚线分隔的总结线（wine 色加粗），起收束作用
5. **禁止增删内容**：拆分只是改变排版结构，不得修改、添加、删除原文的任何文字

### 4.3 视觉规格

| 参数 | 值 |
|------|-----|
| 海报宽度 | 540px（CSS），输出 1080px（2x） |
| 截图分辨率 | deviceScaleFactor: 2 |
| hero 区域高度 | 400px |
| 人脸定位方式 | OpenCV Haar 级联检测 → CSS `object-position` |
| 输出格式 | PNG |

### 4.4 文件命名

- 输出文件名 = `角色名.png`（与 MBTI 报告中的角色名一致）
- 配置文件命名建议：`poster-config.json`，放在对应 workspace 项目目录下

## 五、底层规则

以下规则是保证产出质量的不可跳过的底线约束。

### 规则 1：人脸检测必须作为流程的一部分，不可使用固定 object-position

**原理**：不同角色的剧照构图差异极大——有正脸特写、有侧脸、有半身、有仰角。使用固定的 `object-position`（如 `center 20%`）必然导致部分角色的脸被裁切出画面。

**实现方式**：
- 使用 OpenCV 的 Haar 级联分类器（正脸 + 侧脸 + 水平翻转）自动检测人脸中心
- 将人脸中心的百分比坐标作为 `object-position` 的值
- 检测失败时使用安全默认值 `50% 35%`（偏上居中，适合大多数人像照片）

**注意事项**：
- Haar 级联对侧脸（profile）的检测率较低，必须同时加载 `haarcascade_profileface.xml` 和水平翻转检测
- 检测结果仍可能不准确（如脸部被遮挡、极端光线），校验阶段必须逐张目视确认

### 规则 2：台词选择必须由人工指定，不可自动选择

**原理**：台词的选择是内容判断，涉及"哪句最能代表这个角色"的审美决策，无法通过字数、位置等机械规则替代。

**实现方式**：
- 配置文件中通过 `quotePicks` 字段指定每个角色的台词编号
- 若未指定，fallback 到第一条台词（而非随机选择或"最短的"等自动规则）
- 每个角色只展示一条台词（不堆叠）

### 规则 3：正文拆分只改变排版，不改变内容

**原理**：MBTI 角色分析报告的文字已经过独立的写作和审核流程，海报生成环节无权修改内容。

**具体约束**：
- 不得为了排版美观而删减文字
- 不得为了"更好理解"而添加过渡词
- 不得为了分点均匀而重组句子顺序
- 唯一允许的操作：按标点符号位置断句 + 合并短句

### 规则 4：脚本必须是幂等的且配置驱动的

**原理**：海报生成是会反复执行的流程（调台词、换图片、修正文），每次执行都应该产出完全一致的结果。

**具体约束**：
- 所有可变参数（文件路径、台词选择）收拢到配置文件中
- 脚本不依赖运行时的交互输入
- 相同配置 + 相同材料 = 相同输出
- 输出文件直接覆盖，无需手动清理

### 规则 5：生成流程中不调用 LLM

**原理**：海报生成是确定性的排版任务，所有内容（分析文字、台词、图片）在上游环节已经完成。引入 LLM 会导致产出不可复现、增加延迟和成本。

**唯一需要 LLM 的环节**：当人工校验发现源材料本身有问题（如某段功能解读需要重写），应回到上游的 MBTI 报告生成流程修改，而非在海报生成环节修补。

## 六、经验总结

以下经验来自实际执行中遇到的问题，适用于所有同类项目。

### 6.1 人脸检测

- **Haar 级联器的局限性**：对正面人脸检测率高（>95%），对侧脸/仰角/暗光场景检测率显著下降。必须同时使用 `haarcascade_frontalface_default.xml`、`haarcascade_frontalface_alt2.xml`、`haarcascade_profileface.xml` 三个级联器 + 水平翻转，才能覆盖大多数古装剧照的构图
- **取最大脸**：多次检测会产生大量候选框（同一张图可能检测到 20-60 个框），按面积排序取最大的一个即可——角色剧照通常只有一个主体人物
- **安全默认值**：未检测到人脸时，使用 `50% 35%` 而非 `50% 50%`——人像照片的脸通常在画面上方 1/3 处

### 6.2 正文拆分

- **分号是比句号更好的断点**：中文长段落中，分号 `；` 通常分隔的是同一论点下的并列论据，天然适合拆成分点。句号 `。` 分隔的可能是完整的推理链条，贸然从句号处断开可能破坏逻辑
- **80 字符合并阈值**：经测试，海报宽度 540px 下，单个分点在 40-100 字之间视觉效果最佳。低于 40 字显得碎片化，高于 100 字又失去了分点的意义。80 字符作为合并阈值能较好地平衡
- **最后一句作为总结线**：MBTI 功能解读的写作规范要求"剧情先行、理论收束"，因此最后一句通常是归纳性质的，天然适合作为视觉上独立的总结线

### 6.3 Playwright 截图

- **`deviceScaleFactor: 2`**：确保输出的 PNG 在手机屏幕上清晰锐利。1x 在 Retina 屏上会模糊
- **`waitForTimeout(1000)`**：等待字体加载。系统字体（如 STSong）通常立即可用，但 Google Fonts（如 Noto Serif SC）需要等待网络请求完成
- **截图 `.poster-container` 而非全页**：避免截入 body 的黑色背景。截元素可以精确控制输出的尺寸和边界

### 6.4 工程实践

- **配置文件放在 workspace 项目目录下**（而非 scripts 下）：配置是跟随项目走的，不同影视剧有各自的配置
- **临时 HTML 文件保留在 `scripts/temp-posters/`**：方便调试时直接在浏览器中打开 HTML 检查排版，而不必每次都走完整的截图流程
- **图片文件名必须与角色名完全一致**：这是整条流水线的隐式契约——MBTI 报告、台词表、剧照文件名、人脸检测输出、最终 PNG 文件名，全部通过角色名关联。任何一处不一致都会导致匹配失败
